01 / Incident reports

Find the signal.
Fix the system.

The interesting part is rarely the alert. It’s finding the pressure point underneath it.

Memory pressureHM / 01

The service kept running out of memory at peak.

Heap profiles from pprof pointed at campaign report generation, which pulled everything it needed into memory at once. I reproduced the spike locally from the profile dumps.

I rewrote the report path to work in chunks. The endpoint got a little slower, a trade I made knowingly; the service hasn’t run out of memory since.

pprof · Go · memory profiling

Database stallHM / 02

One DELETE took the whole database with it.

A team was bulk-deleting contacts: 300,000 rows in a single statement. Everything else queued behind it until PostgreSQL stalled.

I moved the work into a Temporal workflow that deletes in 5,000-row batches, so a large cleanup no longer competes with live traffic.

PostgreSQL · Temporal · batching

Lost state on deployHM / 03

A million-recipient broadcast shouldn’t depend on one process staying alive.

The previous in-memory design could lose its place during a deployment.

I led a rebuild around durable Temporal workflows with configurable retries, plus timezone-aware delivery. Progress survived deployments and broadcasts could reach 1M+ recipients.

Temporal · durable workflows · messaging

P0 on-callHM / 04

Slow transactions, one trace at a time.

On the P0 rotation since I joined, most pages start the same way: a New Relic trace with a transaction slower than it should be.

The fix varies—rewriting the SQL, removing N+1 queries, fanning work out across goroutines, or reworking a feature built for yesterday’s data volume—but the loop is the same: trace, reproduce, fix.

New Relic · SQL · goroutines

At the scene: New Relic follows the trace, pprof checks memory, and the P0 pager is usually what opens the case.
